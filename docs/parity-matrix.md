# Frontend/backend parity audit

Audit source: `docs/backend-blueprint.md` v1.1, especially Sections 5, 8, 15, 17, 18.3–18.11 and
Appendix E; the frontend typed client, mock API and routes; shared contracts; and backend controllers,
schemas, permissions, rate limits and tests. Status is evidence-based. An Appendix E row is not
`done` until its parity suite passes in mock mode and against the real local backend.

## Inventory notes

- The supplied 1.1 blueprint is installed at `docs/backend-blueprint.md` and describes roughly
  210 routes. The gateway currently declares 98 HTTP routes across health, configuration,
  identity, communities/assets, chat/DM, content, moderation and reactions. A declared route is not proof of
  complete or production-safe behavior.
- Backend packages other than `gateway` contain package/readme/index scaffolding. Ten shared SQL
  migrations exist, but service-specific schema and migration coverage from the blueprint is
  incomplete. `infra/docker/docker-compose.yml` starts the gateway, Postgres and Redis. A separate
  outbox worker command now exists, but the API/realtime/worker deployment profiles are not wired.
- Validation is uneven: shared kernel and reaction/mention schemas exist, but many controllers
  accept `unknown` and then cast request bodies to records. Several database writes also lack the
  blueprint's membership/role checks. Route presence is not feature completeness.
- Reaction authorization and rate limits exist in `ReactionsService`: asset A:post for writes,
  A:read for users, participant/no-block for DMs, C:mod for clear; write/burst/users limiter
  families. Gateway service and security tests exist; the initial shared API parity suite is now
  `frontend/lib/api/parity.test.ts` and runs against both target modes.
- Route declarations by controller: identity (20), communities/assets (25), chat/DM (12),
  posts/events/lists/boards/campaigns (15), moderation (11), reactions (9), gateway config/dev (2),
  and operational health/readiness/metrics (3). These sum to 98.
- Critical production blockers found in the current code:
  - Request/verify-code now uses generated codes, configured delivery, rate limits and signed
    sessions; refresh rotation and session inventory/revocation are implemented. Signup records
    a self-reported student/alumni status without treating it as verification; complete auth UI
    and end-to-end parity coverage remain incomplete.
  - Community member listing/role management/removal and asset ordering/permission updates now
    exist. Community updates/deletion, asset metadata/rules
    and agreement routes remain absent; additional access-control coverage is still required.
  - Basic chat/DM routes exist, but mention autocomplete and DM mentions, full conversation
    management, DM edit/delete and several required access checks are absent. An authenticated
    `/me/unread` summary now aggregates asset/DM cursors and unseen mentions; the wider messaging
    parity and authorization matrix remains incomplete.
    Chat and DM read cursors now authorize participants and accept the frontend's cursor-less
    requests by advancing to the latest message.
  - Basic post, event, list, board and campaign routes exist; their create/read/write paths now
    enforce asset or member access and validate request bodies. Detail/edit/delete, paging,
    moderation and other workflows specified in Sections 15.9–15.13 remain incomplete.
  - Report queues/resolution, community timeout/ban management and append-only moderation audit
    routes now exist. Global/DM moderation workflows and comprehensive moderation parity tests
    remain incomplete. Resolving a report with `timeout` applies a 24-hour timeout; direct timeout
    and ban routes accept an explicit future expiry.
  - The default runtime starts the gateway; an independent outbox worker command now publishes
    Redis Streams events. Cookie-domain support is configured, but the `launch-api`,
    `launch-realtime` and `launch-worker` profiles and service routing described in the blueprint
    are not fully wired.
- Accordingly, `missing` in the feature rows means the complete blueprint feature is missing or
  incomplete, not necessarily that no similarly named HTTP route exists. No feature is production
  ready based on route presence alone.
- `NEXT_PUBLIC_USE_MOCK` is the only frontend mock selector; the blueprint's `USE_MOCK_*` feature
  flags are not implemented. Shared constants found: `ALLOW_CUSTOM_ASSETS=false`,
  `ADD_ASSET_ROLES`, `QUICK_REACTIONS`, `MAX_DISTINCT_REACTIONS_PER_MESSAGE=20`, and
  `MAX_REACTIONS_PER_USER_PER_MESSAGE=10`. No `MAX_MENTIONS` or frontend `ENABLE_TYPING` flag was
  found. `PROFILE_TABS` is local to the profile view. Backend `ENABLE_TYPING` is a config flag.
- No `frontend/e2e/parity/` Playwright specs exist. The initial Vitest parity suite covers auth,
  sessions and bootstrap API calls through the typed client; it is not sufficient coverage for
  marking any of those feature areas complete. No mock flag was disabled.
- The initial dual-mode harness currently passes seven API-level cases on mock and real backends.
  `pnpm run parity:mock` runs against the frontend mock; `pnpm run parity:real` recreates the
  isolated Docker stack, seeds fixtures and runs the same tests against the gateway. The total
  audit score remains 0/34 until each area's full behavior and access-check matrix is covered.
- `mockApi` implements the typed `ApiClient` surface. The per-row call inventory below names those
  mock handlers; direct local session and stream routes are called outside the typed client.
- Contract match values follow the requested vocabulary: `yes`, `shape differs`, `path differs`,
  `missing`. A backend endpoint that does not exist is `missing`, even if the blueprint has a target
  shape.

## Initial parity result and gap order

- Appendix E: **0/34 done and matching (0%)**. No row has the required two-mode parity spec.
- Backend status: multiple feature areas have partial routes, but **0/34 features are done and matching** because implementations, contracts, authorization or required parity tests remain incomplete. The previous "4 partial rows" count is obsolete now that identity, community, conversation and content controllers exist.
- Prioritized execution plan (dependency order):
  1. Foundations: login/signup/profile setup and sessions (1–3), bootstrap/unread contracts (4), community membership/roles and asset permissions (9–10, 13), uploads (31), then realtime transport/presence (18).
  2. Community and asset surfaces that depend on those foundations (5–7, 11–14), plus blocking/reporting primitives (20).
  3. Conversation features that depend on auth, permissions, blocking and realtime (15–17, 19), followed by notifications (8).
  4. Content and collaboration surfaces (21–27).
  5. Public/private profile behavior, profile editing, account lifecycle and moderation (28–30, 32–33).
  6. Deployment and launch profiles last (34).
  For each row, first add a test that runs against the mock and real backend, then close contract/behavior/access gaps, and only then mark the row done. No row currently satisfies that complete gate.
- Contract work: align shared request/response schemas and fixtures, including the path/body differences above, before implementing remaining routes; do not treat the already implemented reaction/mention schema slice as a completed contract migration.
- Known behavior gaps to verify/fix at the behavior stage: mock reactions are fabricated by a timer; existing-user login still has a profile-completeness setup decision; front-end data and contracts include DOB; unread, default asset, mention row and badge states must be tested against v1.1.
- Behavior fixes in this pass: mock reaction subscriptions no longer synthesize reaction events; existing-account login no longer redirects to setup based on `profileComplete`; the shared catalog is restricted to Appendix A and uses `rules`/`events`/`campaigns` kinds.
- Login follow-up (not complete): the real API client now extracts the gateway's nested auth error envelope, login recognizes `code_invalid`, and both backend and mock return `too_many_attempts` after five invalid codes. Focused unit tests and the mock browser failure-path test pass; real-backend parity remains blocked by the absence of a dual-mode spec and deterministic email-code test setup.
- Signup follow-up (not complete): backend signup now validates age and school before consuming its one-time ticket; gateway regression tests verify failed validation retains the ticket and valid alumni signup consumes it. This is unit/mock coverage only, not a dual-mode parity pass. Changed this pass: `backend/gateway/src/identity.controller.ts`, `backend/gateway/test/identity.controller.test.ts`, and gateway controller test mock typings in `backend/gateway/test/platform.controller.test.ts` and `backend/gateway/test/conversation.controller.test.ts`.
